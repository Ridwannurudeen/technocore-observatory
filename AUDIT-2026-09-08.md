Scope: `9f554e7` (PR #31) and `20231ee..ae07cf2` (PR #32), with `main` and
`HEAD` both verified at `ae07cf29133cc036afae3336a51920f5f2776f1c`. The worktree was clean

## Findings

### BUG — a rebuild lasting more than five minutes can stop this monotonic timer

**Evidence:** `deploy/systemd/technocore-observatory-rebuild.timer:5-8`,
`deploy/systemd/technocore-observatory-rebuild.service:5-13`.

The timer combines the initial `OnBootSec=2min` trigger with
`OnUnitActiveSec=5min`. `systemd.timer(5)`, **OPTIONS**, defines
`OnUnitActiveSec=` relative to when the activated unit was last activated. The same manual's
**DESCRIPTION** says that if the target unit is already active when a timer elapses, it is not
restarted and is simply left running; systemd does not spawn another service instance.

Consequently, if this oneshot is still active five minutes after it started, that expiration does
not activate it again. Because no new activation occurs to establish another
`OnUnitActiveSec=` deadline, this timer can remain elapsed after the service eventually exits. It
does not overlap builds and does not form a tight retry loop; the failure mode is starvation until
some other action activates the service or restarts/re-arms the timer. The service permits a build
to run for 15 minutes (`TimeoutStartSec=15min`), so the timer and service explicitly allow this
case. This is material given the measured 458-second build. The publication lock in
`rebuild.sh:25-28` prevents concurrent rebuild processes but cannot restore a consumed timer
expiration.

### NIT — the new exception handler is not literally exhaustive for JSON input

**Evidence:** `check_staleness.py:46-58`, `check_staleness.py:82-89`.

All ordinary status-file failures are covered by `except (OSError, ValueError)`:

- opening or reading a missing, inaccessible, directory-valued, or otherwise unreadable path
  raises `OSError`;
- invalid UTF-8 raises `UnicodeDecodeError`, a `ValueError` subclass;
- malformed JSON raises `json.JSONDecodeError`, also a `ValueError` subclass;
- a non-object JSON root, a missing field, `null`, or any non-string `valid_until` reaches the
  explicit `ValueError` at line 51;
- a string not exactly parseable as `%Y-%m-%dT%H:%M:%SZ` is converted to the explicit
  `ValueError` at lines 54-57.

There is one concrete data-driven exception outside that tuple: on the repository's Python
3.12.10, sufficiently deeply nested JSON makes `json.loads` at line 48 raise `RecursionError`.
Allocation failure can likewise raise `MemoryError`. Either still makes the oneshot exit non-zero,
so the alarm fails closed, but it bypasses the documented `publication validity check failed`
diagnostic and emits a traceback (or is killed under `MemoryMax=64M`). This is low severity because
the file is generated locally rather than supplied by a public request.

### NIT — the runbook documents the null outcome, but not why a legitimate null alarms

**Evidence:** `snapshots.py:64-80`, `snapshots.py:495-508`, `DEPLOY.md:779-789`,
`test_deploy_assets.py:763-773`.

Failing on `valid_until: null` is the right operational policy. The snapshot contract deliberately
uses null and `freshness: not_observed` when there is no source observation, but a staleness alarm
cannot establish freshness without a deadline; treating that state as success would be fail-open.
The test explicitly pins null to exit 1. DEPLOY.md does document the outcome through “a release
without a readable `valid_until` fails,” so this is not an implementation/documentation mismatch.
It does not explicitly tell an operator that null can be a valid `not_observed` envelope rather
than corrupt JSON and is intentionally alarm-worthy; spelling that out would make diagnosis less
ambiguous.

## Questions with no defect

### 1. Guard assertions and one-derive behavior — no defect

The old `guard_payload_contract` (`guards.py@20231ee:316-417`) derived a standalone payload at
lines 318-330 and then applied the payload-path, optional-prefix, built-in-member, and embedded
projection checks at lines 332-417. The current body removes only that subprocess and preserves
those checks at `guards.py:322-407`; it receives the `data.json` loaded by `main()` at
`guards.py:788-795`, from the same `build_page` invocation that produced the HTML. That is a
stronger pairing because the full payload and embedded projection come from one run.

`build_page` still invokes the deriver with `check=True` (`guards.py:750-767`). `main()` now catches
that `CalledProcessError`, reports up to 300 characters of textual stderr, and returns 1
(`guards.py:778-787`). Thus a first-run deriver failure still fails the build instead of escaping as
an uncaught exception.

For the repository's unchanged `derive.py` and the immutable ledger copy made by
`rebuild.sh:261-273`, there is no ledger input for which the old second invocation deterministically
failed after the first succeeded while the new path passes: both modes call the same
`derive_jsonl` and write the same data, and `--html` merely adds injection afterward
(`derive.py:4887-4904`). What is no longer asserted is the unrelated ability to launch a second,
no-`--html` process. A custom `--derive` program that succeeds only when `--html` is present, or a
transient resource failure on only the second process, could therefore fail the old guard and pass
the new one. That is the removed duplicate execution, not a loss of the deployed payload-contract
assertion.

### 2. Staleness age check and service access — no defect apart from the diagnostic nit above

The release-age block is byte-for-byte unchanged from `check_staleness.py@20231ee:51-56`; it now
appears at `check_staleness.py:75-80`. The new validity condition runs only after it.

The service can read the published file. It runs as `technocore`, points at the current publication,
and explicitly exposes `/opt/technocore-observatory` via `ReadOnlyPaths`
(`deploy/systemd/technocore-observatory-staleness.service:5-10,16-25`). Per
`systemd.exec(5)`, `ReadOnlyPaths=` makes listed paths accessible for reading while refusing writes;
`ProtectSystem=strict` does not make them inaccessible. The builder also normalizes generated
directories to `0755` and files to `0644` (`build_site.py:303-310`).

### 4. Retention arithmetic — no defect

The bounds remain 1,008 releases and 2,147,483,648 apparent bytes (`rebuild.sh:14-15`), and pruning
enforces both while protecting the active and previous releases (`rebuild.sh:209-240`). At the
nominal five-minute cadence, `1,008 × 5 minutes = 5,040 minutes = 84 hours = 3.5 days`, exactly the
README's qualified claim (`README.md:46-50`). Slow or failed builds can make the retained elapsed
span longer, and the independently documented 2 GiB bound can make it shorter; the README already
says both bounds apply.

### 5. Public cadence promises — no defect

No ten-minute publication cadence remains in the public sources examined. The human methodology
states only that validity is source time plus fifteen minutes and frozen input cannot be refreshed
by rebuilding (`site/templates/methodology.html:20`); its cadence language concerns accepted
collector ticks, not static publication (`site/templates/methodology.html:37`). The generated
methodology makes the same distinction (`snapshots.py:1204-1221`). `llms.txt` is generated from
`build_site.py:686-711` and tells clients to inspect source time, validity, and freshness without
promising a rebuild interval. `openapi.json` is generated from `build_site.py:500-653` and likewise
contains no interval promise. The embedded `collection_stall_threshold_seconds: 600` in
`index.html:1559` is the collector's ten-minute stall/honesty threshold defined at
`derive.py:99-104`, not a rebuild cadence. The five-minute timer therefore changes no public
contract; the fifteen-minute validity promise remains unchanged at `snapshots.py:27,64-80`.

### 6. Test discrimination — no defect

All five named additions distinguish the old implementation:

- `test_guards_run_the_deriver_exactly_once` counts subprocesses and requires one
  (`test_deploy_assets.py:1807-1842`); the old body ran two.
- `test_guards_report_a_failing_deriver_instead_of_crashing` requires return 1 and the captured
  stderr diagnostic (`test_deploy_assets.py:1845-1872`); the old `main()` let the first
  `CalledProcessError` escape.
- `test_staleness_check_reads_the_published_validity` (`test_deploy_assets.py:763-800`) has five
  fail-expected cases—overdue, null, non-string, and two malformed timestamp forms—that the old
  age-only script returned 0 for. Its two success cases would also pass on the old tree, but the
  parametrized test as a whole fails there.
- `test_staleness_check_fails_closed_on_a_malformed_status`
  (`test_deploy_assets.py:803-830`) expects failures for invalid JSON and non-object roots; the old
  script never read the file and returned 0.
- `test_staleness_check_fails_closed_without_a_published_status`
  (`test_deploy_assets.py:833-848`) expects exit 1; the old script returned 0 for its fresh release.

The two pre-existing release-age tests now create a future-valid status before invoking the script
(`test_deploy_assets.py:677-760`). They would still pass against the old code—which ignores that
file—but their purpose is to preserve the unchanged age behavior while satisfying the new
fail-closed precondition.

## Verdict

PR #32 is substantively sound: the guard retains its contract coverage while eliminating a
redundant derivation, deriver failures become controlled guard failures, the age check is unchanged,
the validity alarm fails closed on every normal missing/malformed/null case, its sandbox can read
the release, public promises remain accurate, and the new tests discriminate the old behavior. PR
#31's arithmetic and documentation are consistent, but its use of `OnUnitActiveSec=5min` has a
material overrun bug: a single build exceeding five minutes can consume the only re-arm event and
leave publication rebuilds starved. That timer issue should be corrected before relying on the
five-minute change as an availability fix; the two nits do not block the rest of the changes.

## Disposition — 2026-09-08, after the audit

- **BUG (timer starvation): not reproduced; closed.** Tested on the production host (systemd
  255.4-1ubuntu8.10) with a transient timer, `OnUnitActiveSec=60s` driving `/bin/sleep 90`: the
  job started 19:24:15 CEST, ran 90 s past the interval, was deactivated 19:25:45, and the timer
  started it again at 19:25:45. The overrun elapse is not consumed; systemd re-evaluates the
  timer when the unit deactivates and fires immediately when the deadline has passed. The same
  behaviour was observed on the real rebuild timer earlier in the day (build 17:29:29–17:32:26,
  next elapse re-armed to 17:34:31). Consequence for an overrunning rebuild: back-to-back builds,
  bounded by build duration, never a gap.
- **NIT (RecursionError / MemoryError outside the handler): accepted, not changed.** Both still
  exit non-zero; the status file is generated locally.
- **NIT (null `valid_until` wording): fixed** in the "Publication staleness alarm" section of
  `DEPLOY.md`.
